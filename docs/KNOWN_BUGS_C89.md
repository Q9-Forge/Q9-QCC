# Known C89 gaps and bugs

Status: 2026-09-10

This list separates compiler defects from language features that are not yet
implemented. Each entry should eventually have a small reproducer, a fix, and
host plus 68000 coverage.

## Reproduced

| Area | Finding | Status |
|---|---|---|
| Large functions | **Grammar `FAIL` fixed (2026-09-10).** Cause was `memberIncTarget = ident member .` in `Data/qcc.ebnf` -- covered `x.field++` but not `x.field[i]++`/`--x.field[i]`, an ordinary C89 idiom (`vm->state[i]++` in `qrun_vm_run`). Fix: `memberIncTarget = ident member [ index ] .`. Verified via `tools/bootstrap_survey.py` against preprocessed `qrun_vm.c`/`qrun_main.c`: stage 1 (grammar) now 0/56 and 0/42 rejections (previously affected: `qrun_vm_load_ir`, `qrun_push_value`, `qrun_pop_value`, `qrun_vm_run`, `qrun_load_arch_file`). Stage 2 (semantics) also clean once the measurement recipe correctly resolves `qrun_os9.h` instead of stripping all `#include` lines -- see below. Frontend + IR + 68k backend now verified clean for both files (assembly output produced, exit 0); real `r68` assembly and `l68`/Q9-Flux execution not yet verified. | frontend + backend clean, real assemble/link/run open |
| Stage-2 measurement recipe | The original survey recipe stripped ALL `#include` lines before preprocessing, so `qrun_vm.h`/`qrun_ir.h`/`qrun_os9.h` were never resolved -- the 1566/58 semantic findings this produced were mostly `unknown type`/`unknown function` artifacts, not real gaps. Fixed by preprocessing with real header resolution (`-DQRUN_OS9 -ISource`) instead. | fixed 2026-09-10 |
| Complex VM structures | Q9-Run combines structure pointers, array indexing, and large `switch` blocks. This combination is not yet covered by independent C89 minimal tests. | open, add minimal tests |
| `sizeof` pointer types | **FIXED 2026-09-15.** The size depends on the target (68k 4, ARM64 8); the frontend now emits it symbolically as `0+1P` and each backend substitutes its own `P`. See the pointer-size addendum in [ISO_C_GAP_LIST.md](ISO_C_GAP_LIST.md). | done |
| `switch` scope | A declaration directly in a `case` body (`case 1: int y;`) is not scoped to the `switch` block. **Measured 2026-09-15: no action needed.** The form occurs **zero times** in the 4109 Microware sources and not in our own sources either - and C89 does not permit it anyway (a label must precede a statement, not a declaration). Block scoping itself is correct: `{ int y; }` followed by `y` is properly reported as `unknown variable`, inside a `case` as well. | open, but of no practical consequence |
| `switch` fallthrough | **FIXED 2026-09-15.** Previously silently wrong: the case body jumped unconditionally to the end of the switch, so `switch(1){ case 1: r=1; case 2: r=r+2; break; }` yielded 1 instead of 3, with `OK` and no diagnostic. The body now falls into the next BODY (not the next test), behind its `DROP` - on that path the switch value is already off the stack. Eight cases in `runtests.sh` with discriminating expectations (7 = 1+2+4 across three stages). | done |
| Pointer tables with string literals | **FIXED 2026-09-15.** `char *tab[] = {"a","b"}` used to fail SILENTLY in the parser (`FAIL`, 0 diagnostics). New IR opcode `GINITADDR`; on OS-9 the loader relocates the addresses through `M$IRefs`, so such globals now live in the vsect. Came with it: size from the list (`int a[] = {1,2,3}`). | done |
| Nested initializer lists | **FIXED 2026-09-15.** `int m[2][2]={{1,2},{3,4}}` used to fail SILENTLY. The array is flat internally and the braces only group it - but a short row is **padded** to the row length, because `{{1},{2}}` means `m[1][0]=2` in C, not `m[0][1]=2`. Three levels and nesting on a 1D array are reported. | done |
| Comma operator in the `for` head | **FIXED 2026-09-15**: `for(i=0,j=n; ...; i++,j--)`. Previously a silent parse failure. | done |
| Comma operator in statement position | `i = 1, j = 2;` remains a silent parse failure. The change was written (action on `assignItem` rather than `assignStmt`) and left suite and host run green, **but broke self-hosting on the 68030**: the compiler built there emitted `JZ L2080374908` - a garbage label number - and dropped a `STOREP`. It does not show on the host because fresh memory happens to be zero there. Reverted; the `for` head carries the benefit (125 of 4109 Microware sources), this form barely. Root cause not found.  **NARROWED 2026-09-15.** Symptom in the stage2 run: of the TWO labels of a conditional only one is garbage (`JZ L2080374908` instead of `JZ L38`), the second (`L39`) is correct - even though `tcTernaryFalse[]` and `tcTernaryDone[]` are written one after the other and sit next to each other in memory. An overflow from in front would hit both, as would a wrong index; so it looks like a codegen fault on the access to that one array, triggered by the changed parser surroundings. **Ruled out:** the conditional routines themselves (their IR is byte-identical with and without the change), the backend table limits (472/1024 functions, 1792/2048 globals), an over-deep `if` chain (140 consecutive `if` blocks compile correctly) and missing bounds guards on the `tcLogicDepth`/`tcBitDepth`/`tcCastDepth`/`tcTernaryDepth` stacks (all four have one). Reproducible: action on `assignItem` rather than `assignStmt`, then `tools/test_selfhost_68k.sh`. **Narrowed further (second pass):** the faulty `JZ` in `tcTernaryBegin` uses the LOCAL variable `falseLabel` directly, not `tcTernaryFalse[]` - so the garbage originates there and the array merely receives it. That same line reads `TCType condition = tcTypePop(); int falseLabel, endLabel;`: a struct returned by value, immediately followed by two locals of which exactly the FIRST is corrupted. The obvious suspicion - the struct copy writing past its target - is **ruled out**: the same shape as a minimal program (4-byte struct returned by value, then `int f, e;`) runs correctly on the real 68030. The fault needs more context than this shape alone. **THIRD PASS - the question has turned around: this is a FRONTEND fault, not a codegen one.** Comparing the generated 68k assembly of `tcTernaryBegin` with and without the change (both produced under the same output name, otherwise the symbols differ) leaves **exactly one missing instruction**, `move.l (a7)+,-8(a5)` - the store of the post-increment result into `falseLabel`. Comparing the IR of the same function confirms it at the root: **exactly one `STOREL 1`** is missing. So the frontend never emits the store; the backend translates correctly what it is given. The open question is therefore no longer "which codegen path writes past its target" but **"why does `tc_assign` not fire for this one assignment"** - presumably an action dropped from the log when a parse path is rolled back and never re-entered. A minimal program does NOT reproduce it (not even with a struct return, two locals in one declaration and two `if`s before it) - it needs the real parser context. **FOURTH PASS - ONE-LINE REPRODUCER, and my earlier reading was wrong.** With the right criterion (both parsers on the same input, compare the IR) the case shrinks from 310 KB to a single line: `char a; char b; char c; int main(){ a = b = 0; c = 1; putint(c); }` - without the change 3 stores and output 1, with it 2 stores and output 0. **A chain assignment followed by a simple one: the second loses its `STOREGC`.** Either form on its own is correct. That also settles that the change INTRODUCES the fault rather than waking a latent one - without it everything is right. Swapping the alternatives in `assignStmt` (comma list before `chainAssign`) does NOT fix it. The cause therefore lies in the interplay of action log and backtracking: after a successful `chainAssign`, `tc_assign` on `assignItem` no longer fires for the next assignment.| open, cause unknown |
| `union` | **IMPLEMENTED 2026-09-15.** The keyword used to be unknown (silent parse failure). A `union` is REGISTERED as a `struct` whose fields all sit at offset 0 and whose size is that of the largest field - so it inherits field access, `->`, whole-value copy, parameters, returns and arrays without any of that being rebuilt. **Byte order across mixed field sizes is implementation-defined**: 68k is big-endian, the VM oracle little-endian; `u.i=5; u.c[0]` gives 0 there and 5 here. Case 42 of `tools/test_struct_68k.sh` checks it on the target, `runtests.sh` stays deliberately endian-neutral. | done |
| `volatile` | **ACCEPTED 2026-09-15** in the same positions as `const` (local, global, `static`, parameter, struct field). It has no effect of its own - and that is **verified, not assumed**: QCC keeps no values in registers across statement boundaries, and `-peephole` only folds evaluation-stack traffic (A7), never variable accesses. The suite counts this in the generated assembly (two reads stay two, also with `-peephole`). Adding a peephole pattern that merges variable accesses makes exactly this test fail. | done |
| String concatenation | **FIXED 2026-09-15.** `"ab" "cd"` is now one string (C89 3.1.4), across line breaks too - the case that forced long diagnostics in this project's own tools onto a single line. Previously a silent parse failure with no line number. **The gap had to be spelled out in the rule**: `stringLit` is in the TOKEN list and TOKEN rules skip no whitespace, so without `stringSep` only `"ab""cd"` worked. | done |
| Explicit `enum` values | **FIXED 2026-09-15.** `enum E { A = 5, B }` - B is 6. The value resets the counter and the following constants continue from there; negative values work. Previously a silent parse failure. | done |
| Anonymous `typedef enum` | **FIXED 2026-09-15.** `typedef enum { A, B } Flags;` and the tagged form. The tag is parsed and discarded as with `struct` - the typedef target name serves as the name. | done |
| Function pointer as a local variable **and as a parameter** | **FIXED 2026-09-15.** `int (*fp)(int);` without the detour through a `typedef`, including `void` return and several parameters. Previously a silent parse failure. The two parameter lists nest here; that works because the outer one collects through `tc_param` into `tcLocalTypes` and the inner through `tc_externparam` into `tcExternBuildParamTypes` - two separate buffers. **Still open** are the two remaining positions: as a global (the raw-text parser in `tcGlobalOne` does not know the form) and as a struct field; there the `typedef` route (`typedef int (*FP)(int);`) has always worked and is unchanged. | partial |
| `goto` | **FIXED** (measured 2026-09-15): backward (loop) and forward (jump to end) both produce the correct value. | done |

## Boundary

The successful QCC bootstrap does not disprove these findings. The bootstrap
uses prepared source inside the supported subset. Q9-Run is now an independent
larger regression workload for C89 compatibility.

A fix is complete only after this chain passes:

```text
QCC frontend -> IR -> qccvm.py/native VM -> 68k backend -> Q9-Flux
```
