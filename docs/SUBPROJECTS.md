# Subprojects and Priorities

*German version: [SUBPROJECTS_de.md](SUBPROJECTS_de.md)*

The path to an ISO C system is split into separate subprojects. That
keeps the language core manageable, while the preprocessor, library,
optimizer, and target systems can grow independently.

## Decided compiler split

The toolchain, previously bundled together in Q9-QCC, will going forward
be split along its stable file formats and responsibilities:

```text
C source
  -> Q9-cpp     preprocessor
  -> Q9-c0      frontend (lexer, parser, semantics) and IR generation
  -> Stack IR   shared, textual intermediate format
  -> Q9-il68k   stack IR to 68000 assembly in Microware OS-9/r68 format
  -> r68        assembler, produces a .r object file
  -> l68        linker, produces an executable OS-9 module
```

- **Q9-cpp** is a new, standalone preprocessor project. It knows neither
  the parser, the stack IR, nor the backends.
- **Q9-c0** is the C frontend. Its executable contains the lexer and
  parser generated by Q9-Parsec, plus the QCC-specific actions for type
  checking and stack IR generation. Q9-Parsec itself remains the
  generic parser/grammar generator.
- **Stack IR** is the current working name for the line-based,
  stack-oriented intermediate format. A more polished, binding name
  will be decided separately later; until then no new short name is
  introduced.
- **Q9-il68k** is the 68000 target generator. It produces assembly
  source, not an object format and not an executable module.
- **r68** and **l68** remain the Microware tools used for now. Dedicated
  assembler and linker programs are later, separate projects.

The existing ARM64 backend and VM components remain test/reference
tools for now and are not part of this first OS-9 product path.

## Main project: C language core

This project contains the grammar, semantic type model, IR, QCCVM, and
the already-existing target backends, only as far as they're needed to
test the language core.

### Priority P0: work on first

1. String constants and string literals
2. Character, integer, and other literals including constant expressions
3. `typedef` and its associated name resolution
4. `enum` and enumeration constants
5. `struct` with layout and member access
6. Pointer to `struct` and `->`
7. `union` and shared memory layout
8. Aggregate and designated initialization

This order connects syntax, type model, memory layout, and
initialization in small, incrementally building units.

### After that, in the language core

- `const`, `volatile`, `restrict`
- `void` and `void *`
- further integer widths and conversion rules
- `sizeof`, casts, and complete lvalue rules
- `for`, `do/while`, `break`, `continue`, `switch`, `goto`
- function pointers
- function prototypes (bare, without a body), `static` visibility, `extern`
  for global variables, and multiple translation units: **done for
  QCC (2026-07-25)**, see `docs/STATUS.md`/`docs/PROGRESS.md`
  ("multi-file compilation") -- verified live against real `l68` and
  `clang`/`ld` linking, deliberate limit: no `#include` mechanism/header file

## Own subproject: preprocessor

The preprocessor runs as its own program or library ahead of the
parser. It delivers a cleaned-up translation unit to the compiler and
knows nothing about IR or backend details.

Planned stages:

1. Tokenization and line continuation
2. `#define` without parameters
3. `#include` with an include search path
4. `#if`, `#ifdef`, `#ifndef`, `#else`, `#elif`, `#endif`
5. Macros with parameters as well as `#` and `##`
6. Predefined macros and preprocessor error diagnostics

## Own subproject: C standard library and headers

Header files and implementations are not built into the language
grammar. They form a separate runtime/library project with a clear ABI
interface to the compiler.

Planned stages:

- Basic type headers: `stddef.h`, `stdint.h`, `limits.h`, `stdbool.h`
- Memory and strings: `memcpy`, `memset`, `memcmp`, `strlen`, etc.
- I/O: a small `stdio` subset initially
- Memory management: `malloc`, `calloc`, `realloc`, `free`
- afterward math, time, error handling, and other ISO headers

## Own subproject: optimizer

The optimizer operates on a stable IR and only starts once the language
core's semantic tests are broad enough. Possible first passes are:

- constant folding
- removal of unreachable jumps
- local redundant loads/stores
- simple per-backend peephole optimization

Semantic changes do not belong in the optimizer.

## Own subproject: further backends and target systems

New CPU backends, object formats, linker integration, and target
runtimes are planned separately from the language semantics. 68000 and
ARM64 remain test backends for now; Q9, x86-64, or further
architectures get their own packages.
