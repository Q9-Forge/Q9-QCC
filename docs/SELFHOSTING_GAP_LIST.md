# Selfhosting Gap List

*German version: [SELFHOSTING_GAP_LIST_de.md](SELFHOSTING_GAP_LIST_de.md)*

Status: **2026-07-25 (addendum: multi-file compilation done -- that also clears the last "very high" item from section 1)**

## Target definition

Question: which language features and library functions does QCC need
so that the **toolchain itself** (EBNF generator + generated parser)
could eventually be written in QCC and compiled by itself --
"selfhosting" in the classic compiler-construction sense?

This list is NOT derived from the ISO C standard (see
`docs/ISO_C_GAP_LIST.md` for that), but measured directly against the
toolchain's actual source code: it was searched for which C/C++
constructs `Source/parsec.cpp`, `Source/codegen.cpp`, `Source/tiny-regex.cpp`,
and the generated parser twins (`Data/*_p.c`) actually use. We check
items off this list as soon as QCC masters the given feature --
regardless of whether it has a different priority in the ISO list.

## The three selfhosting layers

The data flow (see `docs/ENTWICKLERHANDBUCH.md`) has three very
different building blocks that need to be considered separately:

| Layer | File(s) | Current style | Effort |
|---|---|---|---|
| **L1: generated parser twin** | `Data/*_p.c` (e.g. `qcc_p.c`, 2967 lines) | already almost pure C, generated by `codegen.cpp` via `fprintf` | smallest -- the natural first bootstrap step |
| **L2: the EBNF generator itself** | `Source/parsec.cpp` (2149 lines), `Source/codegen.cpp` (1527 lines), `Source/tiny-regex.cpp` (494 lines) | C-style C++: no STL, mostly fixed global buffers, **since 2026-07-24 with targeted `malloc`/`realloc`/`free`** (see below) | biggest chunk, but architecturally closest to QCC |
| **L3: IR backends** | `Source/qcc_backend.cpp`, `Source/qcc_arm64_backend.cpp` | modern C++: `std::vector`/`map`/`string`/`fstream`/exceptions | its own, different kind of rework -- see below |

**Update 2026-07-24 (Q9 memory footprint):** The earlier finding "L2
needs no dynamic memory management" no longer holds unconditionally.
The cause of the ~34.6 MB data segment (see below) was almost entirely
two fixed tables in `codegen.cpp` (`routinesC`/`routines68k`, each
`ACTION_ROUTINE_MAX=256 × ACTION_ROUTINE_LEN=65536` bytes of text ≈ 32 MB
combined) for the ACTION/ROUTINE action interface -- a size that can
never be properly dimensioned in advance for either an 8/16 MB target
system or very large projects on the host, since the number and length
of routines per grammar are unknown. Solved via `malloc`/`realloc`
doubling (start small, grow on demand, see `pushRoutine`/`growBuf` in
`codegen.cpp`) instead of fixed arrays. Confirmed: the Microware
`clib`/`stdlib.h` (`/Volumes/SSD1TB/projects/REF/SRC/DEFS/stdlib.h`)
provides `malloc`/`realloc`/`free`, so this only affects QCC itself as a
language (see the new row in the table below), not the OS-9 target
platform. All other tables in L2 remain fixed global arrays -- the
hurdle for selfhosting L2 has thus risen somewhat, but not fundamentally:
before an L2 selfhosting attempt, QCC additionally needs a
`malloc`/`free` runtime building block (currently absent, see table).

## Legend

- **missing**: QCC doesn't have this language feature yet (see `PROGRESS.md`/ISO list)
- **partial**: basic functionality present, not yet sufficient for the concrete use here
- **present**: QCC can already do this

## 2. What is NOT additionally needed

- **No real C++ templates/exceptions/STL in the generator itself** --
  those only occur in L3 (see below), not in L2.
- **No variadic function DEFINITIONS** in the generator -- `printf`/
  `fprintf` are only CALLED (library functions), the generator itself
  never defines a function with `...` anywhere. So QCC doesn't need to
  support its own variadic functions right away, only variadic calls
  against a supplied runtime function.

## 3. Library/runtime needs of the generator (not a language feature, but runtime)

**Strategy change 2026-07-24:** Instead of REBUILDING these three points
as a dedicated QCC runtime, the REAL OS-9/Microware `clib.l` functions
are called directly -- provided their calling convention is met. This is
documented in the Ultra-C/C++ processor manual (`DOC/PDF/ultrac_pg.pdf`,
"Passing Arguments to Functions": 1st/2nd argument in `d0`/`d1`, the rest
on the stack in reverse order; for variadic functions like `printf`,
everything on the stack) and deviates from QCC's own (purely
stack-based) internal calling convention. `clib.l` exports symbols under
their plain names without an underscore prefix (`strcmp`, `printf`,
`malloc`, `strlen`, `fopen`, etc., confirmed via `strings`). QCC now has
`extern` declarations for this (no body, just a signature) plus its own
call path in the 68k backend (`CALLEXT`/`CALLEXTP`) that follows exactly
this ABI -- see docs/PROGRESS.md for details. The placement was verified
end-to-end against hand-written mock stubs (no real Q9/`clib.l` access
possible in this environment). The assembler stage needed for this has
likewise since been completed (2026-07-24): an `-os9` output mode in the
68k backend produces code framed with `nam`/`psect`/`ends`, using `*`
full-line comments and `align 4`/`dc.l` (instead of `even`/`ds.l`, which
the real `r68` rejects as "bad mnemonic") -- a test case with DATA/BSS
globals AND an `extern` call (CALLEXT) was successfully assembled into a
relocatable `.r` file by the REAL `r68.exe` (via Wine/REF).

**Real linking + real execution: also done (2026-07-24).** `putint`/
`putuint`/`putchar` call the real, unbuffered `_os_write` syscall from
`clib.l` in `-os9` mode; a test program linked with it ran FOR REAL on
the Q9 emulator and printed the correct values. Along the way, three
independent bugs were found and fixed: (1) the backend used `a6` as its
own frame pointer, even though Microware's ABI reserves `a6` as a static
data pointer for the ENTIRE runtime (`a5` is the real frame register) --
fix only in `-os9` mode. (2) `jsr <name>` for external calls is encoded
by `r68` as absolute rather than PC-relative (breaks as soon as the
module doesn't load at address 0) -- fix: `bsr` instead of `jsr`. (3)
Execution always starts at the first byte of the FIRST file on the `l68`
command line -- `cstart.r` MUST come first, otherwise the program starts
running without any runtime initialization. See docs/PROGRESS.md for
all details (including a fourth, independent bug in the `%` operator
found along the way while debugging). STILL OPEN: string literals in
QCC (without them a real `printf("format", ...)` call with a format
string cannot be written, only with purely numeric/pointer arguments or
via the now-real `_os_write` path).

| Function(s) | Occurrences (count) | Note |
|---|---|---|
| `strcmp`, `strncmp`, `strlen`, `strstr`, `strchr` | approx. 120 calls total in `parsec.cpp`+`codegen.cpp` | core tool for table/name comparison; now callable AND linkable via `extern` declaration against the real `clib.l` (codegen AND linking done, see above) instead of being rebuilt as a QCC runtime |
| `printf`/`fprintf` (text output of the generated code) | `parsec.cpp`: 73, `codegen.cpp`: 236 | the generator is at its core a text generator -- no codegen without formatted output. `extern` declaration + variadic CALLEXT codegen + real linking done; additionally needs string literals (still open) for the format string |
| File I/O (`fopen`/`fread`/`fwrite`/`fclose`) | throughout, for reading the `.ebnf`/`.lextab` and writing the `_p.c`/`.s68` output | calling convention (up to 4 arguments, `fread`/`fwrite`) already verified via the 4-argument test case (2 registers + 2 stack); real linking now also done (see above) |

These three points are the real leverage: even if QCC could do
`struct`/`for`/`switch` tomorrow, it would additionally need a small
standard library (string comparison, formatted output, file I/O) before
the generator would even be runnable -- but the path there is now "wire
up the real `clib.l`" instead of "rebuild it in QCC".

## 4. Additional needs for L1 (selfhosting the generated parser twin itself)

The generated code (`Data/*_p.c`) uses constructs that don't occur in
the generator itself, because the generator only emits them as text:

| Feature | Location in the generator (as an emitted string) | Why L1 needs it |
|---|---|---|
| `goto` + jump labels | `codegen.cpp:865,880,885,894,907,922,932,945,954` (all inside `fprintf(fp, "...goto L%d...")`) | backtracking control flow in the generated recursive parser runs via `goto`/labels, not structured loops |
| Function pointers + a struct with a function-pointer field | `codegen.cpp:1048-1050`: `typedef void (*ActionFn)(const char*, const char*); typedef struct { ActionFn fn; ... } ActionLogEntry;` | the ACTION/ROUTINE mechanism (backtracking-safe action log, see the `ebnf-projekt.md` memory) depends directly on function pointers |

In other words: **layer 1 is NOT simply a subset of layer 2** -- `goto`
and function pointers are mandatory for the generated parser, even
though the generator itself never needs them in its own logic.

### Re-measurement with a two-stage survey (2026-08-12)

The claim above that "all measured language gaps are closed" was correct
only for the five constructs that had been counted -- and for function
pointers it was **too optimistic**. Two things had to be fixed before any
number could be trusted:

**Semantic errors were not fatal.** The generated parser reported
`qcc: unknown function`, type errors and everything else on stderr, but
exited with **0**, printed `OK` and emitted the (wrong) IR anyway. A chain
`qcc_p x.c > x.ir && qcc_backend x.ir` therefore produced wrong code
without complaint. The counter `tcSemanticErrors` existed, was incremented
163 times and read **nowhere**. This is not a QCC quirk but a gap in the
generator: every grammar with actions had it. `Source/codegen.cpp` now
declares `actionErrors` in the generated parser and checks it after the
replay. See the three closing words `OK`/`SEMERR`/`FAIL` in the README.

**The survey therefore has two stages now** (`tools/bootstrap_survey.py`):

| Stage | Measures | Method |
|---|---|---|
| 1 | Does the grammar accept the text? | units fed **cumulatively**, evaluates `FAIL` only |
| 2 | Is it also meaningful? | the **whole file** in one run, evaluates the exit code |

Stage 1 must not evaluate semantic errors: a prefix legitimately contains
unresolved forward references. Mixing the two turned 5 reported gaps into
346.

Measured state (2026-08-12, after member access on function return values
was added -- `callMember`/`tc_callmember`, developed in parallel by another
session):

| Target | Units | Stage 1 accepted | Stage 1 gaps |
|---|---:|---:|---:|
| `Data/qcc_p.c` | 768 | **768** | **0** |

**Stage 1 on the bootstrap target is empty for the first time** -- the
grammar accepts `Data/qcc_p.c` completely. An intermediate measurement a few
hours earlier still showed 4 gaps, and all four failed on the same construct
(`tcPointee(bt).base` in `tcMemberIncDec`, `tc_varref`, `tc_term`,
`tc_target`); closing it closed all of them at once.

**Stage 2 is therefore measurable for the first time**: 30 distinct
complaints. Read them with care, several are artifacts of the measurement
setup rather than compiler gaps:

- `unknown function`, `unknown type name 'FILE'` and the cascade of `?`
  types that follows are consequences of the preprocessing used here, which
  strips `#include` lines. The remedy is already recommended above: replace
  the 2 `#include`s with `extern` declarations before reading stage 2.
- Genuine gaps in that list: `multi-dimensional struct arrays`, `partial
  indexing of a 2D/3D array`, `chained assignment is only supported for
  plain variables`, `cannot assign through pointer to const`.
- **And one self-inflicted one**: `a comma expression must end in a value,
  not an assignment` -- see the comma operator note below.

**Correction to the function-pointer entry above.** `CALLIND` did work via
an array element (`t[0](7)`) and a struct field (`s.f(3)`). Broken was the
call through a plain **variable or parameter** (`Fn f; f = g; f(7);`) --
and silently so: the IR contained `PUSHFN g / STOREP 0 / PUSH 7 / DROP`,
no call at all. Cause: the grammar tries `call` before `indirectCall` in
`callStmt`, and for a bare identifier the direct rule matches. Fixed in
`tc_callname`, i.e. **before** the arguments -- the only possible place,
because the backend expects the pointer at the bottom (it reads it at
`nargs*4(a7)`).

Why this survived so long: **`tools/qccvm.py`, the IR reference oracle
behind `tc_check`, knew neither `PUSHFN` nor `CALLIND`.** Function pointers
were never covered by the suite at all -- not even the paths that worked.
Whoever closes a language gap must check whether the oracle can execute the
opcode.

**Comma operator closed (2026-08-11).** Deliberately only *inside*
parentheses (`factor = parenOpen commaExpr parenClose`): in C the grammar
separates `expression` (with comma) from `assignment-expression` (without),
and argument lists and initialisers use the latter -- misreading a comma in
`argList` as an operator would be a silent error. The trap here was not the
grammar but the **target state**: `tc_target`/`tc_assignop` write into
globals, so an inner assignment took them away from an enclosing one
(`x = (y = 1, 2)` put 2 into `y` and 0 into `x`). Saved in the parenthesis
frame, which already has a depth stack; the single-level `tcPrevTarget*`
buffer is not enough for `(y = (z = 1, 2), 3)`.

**The declared "deliberate limit" of that change does not hold up and is the
next thing to fix.** It says the last operand must yield a value, so
`(x = 1)` is diagnosed. Stage 2 shows the real target hits exactly that --
and it is no exotic case but plain C: `if ((p = f()))` and
`while ((c = g()))`. Before the comma operator existed these were a parse
error, so this is no regression, but the limit has to go: a parenthesised
assignment must yield the assigned value. That means supporting assignment
as an expression rather than only as the left operand of a comma.

Next steps, in order:

1. Parenthesised assignment yields a value (`if ((p = f()))`) -- removes the
   self-inflicted stage-2 complaint.
2. Replace the 2 `#include`s in the bootstrap copy with `extern`
   declarations, so stage 2 stops reporting phantom `unknown function`s.
3. Then work through the genuine stage-2 gaps.

### What "bootstrap" precisely means (terminology, 2026-08-10)

Important, because it's easy to confuse -- the selfhosting loop closed
on 2026-08-10 (see `docs/STATUS.md`) is **not** a compiler bootstrap:

- **Stage 0** (done, built 2026-07): `xcc` -- the Microware K&R/Ultra C
  compiler -- builds QCC for OS-9. That's why `qcc_p` and `qcc_backend`
  exist as runnable OS-9 modules on Q9 (see `OS9_BOOTSTRAP.md` in
  Q9-Parsec, which assumes their existence but does not describe a build
  path).
- **Intermediate step** (done 2026-08-10): QCC correctly translates a
  large, real third-party program -- the EBNF generator. That's a
  maturity proof for the compiler, not a bootstrap.
- **Stage 1** (open): QCC translates QCC's OWN source code
  (`Data/qcc_p.c` + `Source/qcc_backend_c.cpp`). Blocked by the three
  gaps in the table above.
- **Stage 2** (open): the compiled output from stage 1 translates the
  source code again. A bootstrap counts as proven only once stage 1 and
  stage 2 produce bit-identical output (a fixed point).

Per Andreas' decision (2026-08-10), this remains a long-term goal and is
not being pursued for now.

## 5. L3 -- the two C++/STL backends (a different kind of rework)

`Source/qcc_backend.cpp` and `Source/qcc_arm64_backend.cpp` are the
newest files in the project and the only places with real "modern" C++:
`std::vector`, `std::map`, `std::string`, `std::ifstream`/`ofstream`,
`std::runtime_error`/`invalid_argument`, `std::stoi`, `std::to_string`.

This isn't a language-feature backlog but an architectural question:
selfhosting these files would require

- replacing `std::vector`/`map` with fixed-size arrays + linear search
  (exactly the style `parsec.cpp`/`codegen.cpp` already use consistently),
- replacing `std::string` with fixed `char[]` buffers + the string
  runtime from section 3,
- replacing exceptions with return codes/error flags (as the rest of
  the toolchain already does),
- replacing `ifstream`/`ofstream` with the same file I/O runtime as L2.

**Recommendation:** L3 doesn't necessarily need to be part of a first
selfhosting milestone -- a compiler that initially only selfhosts the
frontend + generator (L1+L2) and continues to run the final machine-code
generation through a host-side C++ compiler is a legitimate intermediate
step (many real selfhosting compilers have done exactly that).

## 6. Real compile/execution test with the target toolchain (2026-07-23)

Instead of only analyzing, it was tried out: the complete generator
(`parsec.cpp`+`codegen.cpp`) was actually compiled and linked with the
real Microware `xcc` toolchain (which Q9 itself uses). Result:
**works**, with three concrete findings for the selfhosting path:

- **C++ templates were the only real blocker in language scope.**
  `Source/msvc_compat.h` had template overloads (array-size deduction
  for `strcpy_s`/`strncpy_s`/etc.) that crashed `xcc`'s compiler (Ultra
  C/C++ 2.5, built 2001) with an internal error. Since templates
  otherwise occurred nowhere else in the project, all 75 affected call
  sites were switched to an explicit `sizeof()` form and the templates
  removed (PR #11, permanently in the repo) -- works identically on all
  platforms.
- **Comment style is a pure cross-compiler problem, not a language
  feature.** `xcc` doesn't accept C99 `//`, only `/* */`. The xcc test
  run needed a string-literal-aware converter (a naive line regex
  destroys `"//"` string values, which occur as grammar configuration
  data in the project!). This conversion is NOT in the repo, only
  applied once for the xcc test run -- a permanent solution (e.g. a
  dedicated build step or switching the comment convention) is still
  open.
- **Data segment size is the real blocker for execution.** The linked
  module needs ~34.6 MB of data segment (fixed global buffers,
  generously sized for a modern Mac), but the Q9 target system only has
  16 MB RAM. Compiling+linking still works (32-bit instead of 16-bit
  data references are needed via `xcc -tp=68030,ld`, since plain
  addressing alone would otherwise fail at the 64 KB boundary), but
  startup on the real system fails. Full details and the exactly
  reproducible procedure are in the Claude memory file
  `q9-xcc-toolchain-milestone.md`.

In other words: the language-feature roadmap from section 1
(struct/typedef/enum/for/switch/...) is largely worked through, but for
a TRULY runnable selfhosting result there's one more, so-far-uncaptured
point: **shrinking the memory footprint of the static buffers for the
target system.**

## Recommended order

1. **Language features from section 1** to be caught up in QCC: `struct`
   with mixed scalar field types, array fields, AND direct `rec.name[i]`
   indexing (done, 2026-07-24), `typedef` including
   `typedef struct { ... } Name;` inline (done, 2026-07-24), `enum`
   (done), `for`/`switch` (done), `static`/`const` (done, 2026-07-24,
   see docs/PROGRESS.md for the deliberate restrictions),
   multi-dimensional arrays including 3D+ (done, 2026-07-24,
   `TC_MAXDIMS=6`) -- **this point is thus complete for ALL cases that
   actually occur in the generator, and generalized beyond that.** Still
   open (small scope, not a blocker for the generator itself): `union`
   (only 1 occurrence), pointer fields/nested structs.
2. **Connect the mini runtime from section 3**: instead of rebuilding
   string comparison functions, formatted output, and file I/O in QCC,
   call the real `clib.l` functions directly (strategy change
   2026-07-24). `extern` declarations + Microware ABI call codegen
   (CALLEXT/CALLEXTP), the `-os9` r68 output mode, real `l68` linking
   against `clib.l` (including real execution on the Q9 emulator) AND
   string literals (including as a `printf` format string, including a
   variadic-call ABI bug found and fixed on real Q9) are all done
   (2026-07-24) -- **this point is thus complete.**
3. **Memory footprint of the static buffers** (section 6) for a real
   16 MB target system: **done (2026-07-24)** and confirmed live on the
   real Q9 emulator (data segment ~34.6 MB -> ~1 MB, `ebnf_gen` runs
   without errors), see docs/STATUS.md.
4. **Multi-file compilation** (section 1, last item): **done
   (2026-07-25)** -- this completes the entire language-feature roadmap
   from section 1. The reconstructed generator could now, in principle,
   be split across multiple files just like the original (known limit:
   no header file/signature consistency check by the real linkers, see
   docs/STATUS.md).
5. **L1 additional needs** (`goto`, function pointers, section 4) only
   once the generated parser twin is actually meant to be selfhosted --
   not before, to avoid pulling forward language features that aren't
   even needed for L2.
6. **L3 (STL backends)** deliberately deferred or kept permanently
   host-side (see the recommendation in section 5).

This order overlaps heavily with stage A/B of `ISO_C_GAP_LIST.md`
(`struct`/`enum`/`typedef`/`for`/`switch` are already listed there as
"very high"/"high" anyway) -- so the two lists pull largely in the same
direction, except this one additionally makes visible the concrete
library and multi-file needs of the tool itself.
